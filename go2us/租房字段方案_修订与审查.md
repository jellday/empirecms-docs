## 一、十项审查问题逐条回应

### 1. `availdate` 重新设计（独立 `availmode` + 真实 `DATE`）
**原设计问题**：`availdate int` 混用 0/1/YYYYMMDD 三种语义，且"三天后自动归入可立即入住"依赖查询计算，语义不清。

**修订方案**：
- 新增 `availmode` `tinyint`：**0=面议 / 1=立即入住 / 2=指定日期**（明确三种情况）。
- 新增 `availdate` `date`（**可空**，非 NOT NULL，避免 `0000-00-00` 在严格模式报错）：仅当 `availmode=2` 时有效，存真实日期。
- "可立即入住"筛选规则（动态，无需定时任务）：
  ```sql
  WHERE availmode = 1
     OR (availmode = 2 AND availdate <= CURDATE() + INTERVAL 3 DAY)
  ```
  （原设计把"面议"也算入可立即入住，已修正为不纳入；"面议"作为独立筛选项。）

### 2. `renttype` / `lease` 移除方案（结构化字段）
**原设计问题**：把"整租/合租/短租/转租"全部塞进单一 `ttid`，无法表达多维度。

**修订方案**（三个独立业务维度，全部为主表字段、可筛选/列表）：
| 字段 | 含义 | 枚举 |
|---|---|---|
| `rentaltype` | 出租方式 | 0未设 / 1整租 / 2合租单间 |
| `rentterm` | 租期类型 | 0未设 / 1长租 / 2短租度假 |
| `issublet` | 是否转租 | 0否 / 1是 |

**标题分类（ttid）定位**：把"出租方式"维度做成标题分类用于导航页（整租/合租单间，mid=8，*已确认保留 ttid 导航*）。短租度假、转租改为字段，不再依赖单一 ttid。

### 3. 房源状态与 CMS 审核状态分离
**核心澄清**：二者是不同层面，必须区分。
- **CMS 审核状态**（帝国内置，由信息所在表 + `checked` 决定）：待审核（`phome_ecms_info_check`）、已发布（主表 + `phome_ecms_info_index.checked=1`）、归档（`phome_ecms_info_doc`）。这是工作流状态，**不可自定义业务语义**。
- **房源状态** `listingstatus`（新增业务字段，主表）：**1=招租中 / 2=已出租 / 3=已下架 / 4=已过期**。
- **关系**：列表必须同时满足 `index.checked=1`（CMS已审）**且** `listingstatus=1`（招租中）才公开；已出租/已下架/已过期无论审核状态均隐藏。"已过期"可由周期脚本或展示时动态判定（非必需 cron）。
- **原设计纠正**：原 `WHERE checked=1` 直接查主表会**报错**——`checked` 不在主表，而在 `phome_ecms_info_index`。正确列表联表写法：
  ```sql
  SELECT i.* FROM phome_ecms_info i
  JOIN phome_ecms_info_index idx ON i.id=idx.id
  WHERE idx.checked=1 AND i.listingstatus=1 AND i.classid=?
  ORDER BY i.newstime DESC LIMIT 20;
  ```

### 4. 租金原始金额与报价周期
**原设计问题**：按周/晚输入时直接折算为月，丢失原始价格与周期。

**修订方案**（保留原始值 + 归一化值）：
- `rentperiod` `tinyint`：**1=月 / 2=周 / 3=晚**（报价周期）。
- `rent_orig` `mediumint unsigned`：按 `rentperiod` 报价的**原始金额**（如周租\$300 则存 300）。
- `rent` `mediumint unsigned`：**归一化月租**（用于价格区间筛选/排序），0=面议。折算系数（**已确认**）：周×4、晚×30（取整简化，便于人工核对；仅影响排序/筛选，不改变展示的原始价 `rent_orig`+`rentperiod`）。
- 展示用 `rent_orig`+`rentperiod` 显示"$300/周"；筛选用 `rent`。原始价格与周期均不丢失。

### 5. 联系方式公开方式 + 服务端访问控制
- 新增 `contactshow` `int unsigned`（副表）：**隐藏掩码**，0=全部公开已填项；位：1phone 2email 4wechat 8qq 16whatsapp 32line 64telegram 128signal 256skype 512facebook 1024instagram。默认 0（发布者可按需隐藏某些方式）。
- **服务端访问控制设计**：
  1. 联系方式只在详情页展示，且仅对 `listingstatus=1` 且 `checked=1` 的房源。
  2. 模板**不输出**被隐藏方式（不是 CSS 隐藏，避免在 HTML 中留下可被爬虫抓取的明文）。
  3. 建议增加 AJAX 端点 `/e/extend/contact/show.php?id=N`：验证房源活跃后再返回"已公开"的联系方式，防止搜索引擎/机器人批量抓取。该端点读取 `contactshow` 掩码过滤。*（端点到审核通过后再实现，本期先定字段与掩码）*

### 6. `pets`/`parking`/`furnished` 等枚举"未填 vs 否"混用
**修订原则**：**0 = 未设置/未知/不适用**（默认），明确"否/无"用独立值（通常=1），彻底分离"未填"与"否"。

| 字段 | 枚举（0=未设） |
|---|---|
| `furnished` 家具 | 0未设 / 1无家具 / 2部分家具 / 3家具齐全 |
| `parking` 车位 | 0未设 / 1无车位 / 2车位 / 3车库 |
| `laundry` 洗衣 | 0未设 / 1无 / 2房内洗烘 / 3接口 / 4楼层公用 / 5院内 |
| `pets` 宠物 | 0未设 / 1不可养 / 2可猫 / 3可狗 / 4猫狗均可 |
| `proptype` 房屋类型 | 0未设 / 1公寓 / 2独立屋 / 3联排 / 4康斗 / 9其他 |
| `tenantpolicy` 入住政策 | 位掩码，0=均未设 |

> 原设计把 `pets=0` 当"不可养"、把"未填"与"否"混为一谈，已纠正。

### 7. `minterm` / `maxterm` 存储一致性
**原设计问题**：`minterm` 在主表、`maxterm` 在副表，不一致。

**修订方案**：`minterm` 与 `maxterm` **均移至主表** `tinyint`，0=不限，单位=月。理由：租期筛选（"至少租6个月"）需在主表；二者同表保证数据模型一致。（短租的"最少晚数"暂不单列，由 `rentterm=2`+`rentperiod=3` 表达；如需可后续加 `minnights`——*待核实*。）

### 8. `zip` 迁移核实
**实际证据**（见 B）：`zip` 确在**副表**（`tbdataf=1`，`phome_ecms_info_data_1`），`varchar(9)`。
- **tbdataf 真实含义**（官方数据字典确认）：`0=主表 / 1=副表`。副表字段帝国列表/搜索/结合项**不支持**调用，仅详情页可用。
- **迁移必要性**：因地图与 zip 检索需要，**已确认迁主表**（负责人决策）。草稿按主表 `varchar(10)` + 历史回填 + `enewsf.tbdataf=0` 实现。
- **ZIP+4 长度**：标准 ZIP+4 带连字符为 `12345-6789` 共 **10 字符**，`varchar(9)` 会截断。已改为 `varchar(10)`（保留连字符可读性）。
- **历史回填**：`UPDATE 主表.zip FROM 副表.zip WHERE 主表.zip='' AND 副表.zip<>''`（测试库实证迁移 90/5831 条）。副表 `zip` 列**保留不删**（向后兼容）。
- **风险**：须同步 3 张主表 + 改 `enewsf.tbdataf=0`；已在草稿中处理。

### 9. 实际 CMS 表名/模型ID/标题分类/主副表与审核归档关系（实地核实，不靠假设）
见 B 节。**关键纠正**：原 `final.sql` 假设的 `tid=8`/`tbname='info'`/`mid=8` **经数据库实证全部正确**；标题分类表当前**为空**（无记录）。

### 10. 六个索引重评估（附 EXPLAIN）
见 F 节。原 `idx_list(classid,listingstatus,ttid,newstime)` 因 ttid 不再是主维度、且漏了 `checked` 联表问题，已重构为 8 个更精准的索引，并实测全部被优化器选用。

## D. 旧字段→新字段迁移映射与历史数据处理

本模型此前**无租房专属字段**，故无"旧租房字段→新字段"的转换。仅两类物理变更：
| 旧 | 新 | 处理方式 |
|---|---|---|
| `zip`（副表 `varchar(9)`） | 主表 `zip varchar(10)` | 主表加列 + 历史回填（实测 90/5831 条） + `enewsf.tbdataf=0`；副表列保留 |
| `phone`（副表 `varchar(12)`） | 副表 `varchar(30)` | 仅改类型，数据无损 |

**历史数据无法自动转换的处理**：
- 5831 条现有记录的新字段（rent/bedrooms/pets 等）将取默认值（多为 0/空）。这些记录**不会凭空获得真实租房属性**，需后续由发布者编辑或运营批量补录。
- 建议在迁移后导出"新字段全为默认"的清单，交由运营/编辑**人工核对补填**（特别是 rent/beds/pets 等影响筛选的字段）。
- 不做任何破坏性操作：不删旧字段、不清空数据、不删记录。

## E. SQL 文件、执行前检查、执行后验证、回滚脚本

**文件**：`rental_fields_revised_draft.sql`（修订草稿，幂等，按列/索引/记录存在性判断）、`rental_fields_rollback.sql`（回滚，已实测可逆）。

**执行前检查（生产）**：
1. 整库备份：`mysqldump -uroot -p usinfo > usinfo_bak_$(date +%F).sql`
2. 确认 mid=8 / tbname=info（已实证）；确认 `phome_enewsf` 中无同名新字段冲突。
3. 确认 `e/admin` 后台可访问（本机升级副本缺此目录，**建议优先用后台"管理字段"逐字段增加**作为最安全路径，SQL 作补充/可复现记录）。
4. 确认生产为 MariaDB 10.4（零日期默认可接受；MySQL 8 严格模式下的零日期报错**不会在 MariaDB 出现**——见 F）。

**执行后验证**：执行草稿末尾自检（主表新列=24、副表=10、登记=34、zip回填>0、索引清单、标题分类） + 联表列表查询 `checked=1 AND listingstatus=1` 抽样。

**回滚**：`rental_fields_rollback.sql`（DROP 新列/索引、删登记/分类、还原 zip 与 phone）。**已实测**：测试库主表新列与登记均归零、zip 登记还原为副表、副表 zip 列保留。终极回滚＝整库备份恢复。

> **强烈建议执行路径**：后台"数据表管理→管理字段→增加字段"（自动处理主/审核/归档/副表+临时表+缓存）逐个加字段；zip 迁移与索引用本 SQL。原因：手工 ALTER 未覆盖的 `phome_ecms_infotmp_info` 临时表，帝国后台增加字段会自动处理（见 B/F 风险）。
